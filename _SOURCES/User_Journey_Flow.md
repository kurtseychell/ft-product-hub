# Product Hub — User Journey Flow

> **Document purpose:** This document extracts the user journeys embedded in the 20 canonical screens (`/screens/A01.html` through `/screens/Z01.html`). It maps who does what, in what order, with which screen, and how artifacts move through their state lifecycle. It is the connective tissue between the screen inventory and the product story.
>
> **Source of truth:** The HTML screens in `/screens/` are canonical. Where this document and the screens disagree, the screens win.
>
> **Conventions used:**
> - `[B01]` = reference to a screen file (e.g., `screens/B01.html`)
> - **PERSONA** in caps = role acting in that step
> - `→` = transition to the next screen
> - `↦` = state transition on an artifact
> - Lifecycle versions are written as `v1, v2…` to mirror the in-screen labelling (e.g., Brief v3, PRD v9 Final)
> - **PM-BOT** = umbrella brand for all AI surfaces (formerly seen in screens as "Luminary AI", "AI Assistant", "LLM Spec Assistant"). Specialist sub-roles: PM-BOT · PRD Agent / Research Agent / Spec Agent / Design Agent / Test Agent / Release Notes Agent / Bug Replication Agent. The three RICE agents (Market Analyst, Technical Feasibility, Business Strategy) keep distinct names as a council under the PM-BOT umbrella.
> - **Product Hub** = canonical product brand. Replaces 8+ alternates seen across screens (Kinetic Luminary, Architect Intelligence, Precision Curator, Enterprise Hub, Product Console, Product Admin, Product Ops, SaaS PM Backoffice).

## 2. Artifact Lifecycle

The platform is organised around six named artifacts (Brief, PRD, RSD, Spec Items, Design Screens, Backlog Item, Release Note). Each has its own state machine; the screens visualise transitions explicitly with badges.

### 2.1 Brief
The seed text the Stakeholder writes. Becomes the source-of-truth input for AI generation (PRD or RSD depending on Request type).
- States:
  - `v1 (Draft)` — Stakeholder editable
  - `v1 (Submitted)` — enters Request Review queue
  - `v1 (Locked for Review)` — once PM review starts, Stakeholder can no longer edit v1
  - Stakeholder may create `v2 (Draft)` in parallel and submit it independently — does NOT auto-supersede v1; needs explicit Stakeholder confirmation (see §9.2)
- Created at: `[B01]` "Submit & Open PRD Builder"
- Visible at: `[B02]` left panel ("Source of Truth" badge)
- For Type=Bug requests: the Brief becomes the seed for an RSD instead of a PRD — see §2.7

### 2.2 PRD Document
Generated by **PM-BOT · PRD Agent** from the Brief, edited via chat in the PRD Builder.
- States: `Draft (vN)` ↦ `In Review` ↦ `Approved / Final (vN)` ↦ `Archived`
- **Submission Score** (0–100) computed continuously by a small algorithm (see §9.1 OL-5; algorithm spec to be drafted separately). **Purpose:** signals to the Product team when the PRD is ready for review.
- Versions are immutable snapshots; the Version History drawer `[B04]` lets users view + diff
- Final state shows in `[B03]` ("Marked Final v9, Score 87/100") and `[B04]` (status badge)

### 2.3 Spec Items (SpecKit)
Per-PRD set of typed, reviewable engineering specs.
- Types: `API`, `Data Model`, `UI Component`, `Business Logic`, `Integration`
- States per item: `Draft` ↦ `In Review` ↦ `Approved` ↦ `Needs Revision`
- **AI Confidence** (`High / Medium / Low` per item). **Purpose:** signals when the spec meets Definition of Ready for engineering planning / development.
- "Transformation Velocity" `[C03]` shows accuracy-to-PRD as a percentage

### 2.4 Design Screens
Per-PRD set of UI mockups generated against the UI Component specs.
- States: `Generating` ↦ `Draft` ↦ `Reviewed` ↦ `Approved` ↦ `Pushed to Figma`
- Each screen has multiple variants; one is `active`
- Linked to PRD section + Spec ID

### 2.5 Backlog Item / Task
The work unit that flows into delivery. Carries `Type ∈ { Feature, Bug }` (Feature for New Idea / Change Request; Bug for the bug pipeline).
- Pipeline states: `New` → `Under Review` → `Approved` → `In Development` → `Released` (Kanban columns in `[D01]`)
- Cross-cutting attributes: `RICE Score` (Features) **or** `Bug Severity Score` (Bugs — see §9.2 OL-B3), `Research Recommendation` (Pursue/Defer/Reject; Features only), `Domain Priority` flag
- Domain backlog item additionally carries: `domain_rank`, `domain_notes`, `domain_priority_flag` `[D02]`

### 2.6 Release Note
Authored from the set of PRDs (and resolved Bugs) included in a release.
- States: `Draft` ↦ `Scheduled` ↦ `Published`
- Distribution channels: Email · Slack · In-App · Confluence
- Audience targeting: Internal Stakeholders / External Customers / Engineering Team

### 2.7 Reproduction Steps Document (RSD) — bug-path artifact
Created when Stakeholder submits a Request with `Type=Bug`. The bug-path analog of the PRD.
- Generated by **PM-BOT · PRD Agent** (or a Bug-Triage variant — see §9.2 OL-B7) from the Bug Brief
- Captures: environment context, expected vs. actual behaviour, detailed reproduction steps, severity / impact estimates
- States:
  - `Draft` ↦ `In AI Replication`
  - ↦ `Replicated by AI` (success) **OR** `Replication Failed (handed to human)`
  - From "Failed" branch: ↦ `In Manual Replication` ↦ `Reproduced` **OR** `Cannot Reproduce`
  - From either Reproduced state: ↦ `Triaged` (enters `[D01]` Backlog with `Type=Bug`)
- No screens exist for this flow yet — see §9.2 OL-B4

## 3. End-to-End Journey (the canonical happy path)

Numbered steps with the actor, screen, action, and resulting state change.

### Stage A — Access
**Step 1.** **STAKEHOLDER** signs in at `[A01]`. Whitelisted email enforced.
**Step 2.** Lands on `[A02]` Dashboard → sees pipeline KPIs and "New Product Entry" CTA → clicks it.

### Stage B — Stakeholder Intake & Routing
**Step 3.** **STAKEHOLDER** lands on `[B01]` Submit Request.
- Selects request type: **New Idea** (default) / Change Request / Bug
- Writes a `Title` and `Brief` (the brief is explicitly called the *source of truth*)
- Optionally attaches files
- Clicks "Submit & Open PRD Builder"
- Artifact state: `Brief ↦ v1 (Submitted)`, `Status: Request Review`
- **Routing:**
  - `New Idea` / `Change Request` → continues to Step 4 (PRD path)
  - `Bug` → continues to Stage B-Bug (RSD path)

### Stage B (Idea / Change) — PRD Drafting
**Step 4.** **PM** (or Stakeholder, depending on permissions) opens `[B02]` PRD Builder.
- Left panel: Brief (e.g., `v3`). Status `Locked for Review` once PM review begins — Stakeholder cannot edit `v3` from this point. Stakeholder can submit a `v4` Brief in parallel; if they do, an explicit "Supersede current PRD review with v4?" prompt will fire (UX TBD — see §9.2 OL-B1).
- Middle panel: chat with **PM-BOT · PRD Agent**
- Right panel: live document being constructed (e.g., `v7`, 68% complete)
- AI proposes structure (Problem Statement → User Cohorts → Trigger Logic → …)
- PM iterates via chat ("Add Support Teams as secondary user group")
- **Submission Score** updates as completeness improves (algorithm spec TBD per §9.1 OL-5)
- When complete, PM clicks "Mark as Final"
- Artifact states: `PRD ↦ v9 Final`, `Score: 87/100`, `Status: PRD Review`

**Step 5.** **STAKEHOLDER** sees progress at `[B03]` Request Tracking.
- Lifecycle pipeline: `Submitted ✓ → PRD Built ✓ → PRD Review (current, assigned to Sarah Chen) → RICE Scoring → Backlog Approved → In Development → Released`
- Sees PRD summary card with TOC, "View Full PRD" button
- Brief lock status visible (badge: "Locked for Review")
- Activity feed shows assignment and version events
- Comment thread for clarification questions

### Stage B-Bug — Bug Reproduction Pipeline (NEW; no screens exist yet — see §9.2 OL-B4)
**Step 3-Bug-1.** STAKEHOLDER's Bug submission auto-routes to a **Bug Workspace (TBD screen)**.
- **PM-BOT · PRD Agent** generates a draft Reproduction Steps Document (RSD) from the Brief
- RSD captures: environment, expected vs. actual, repro steps, severity estimate

**Step 3-Bug-2.** **PM-BOT · Bug Replication Agent** attempts to replicate.
- Mechanism TBD (sandbox spin-up? automated test harness against captured steps? log query?)
- Cost-managed — likely a token/runtime cap per attempt (see §9.2 OL-B2)
- Output: `Replicated by AI` (with evidence) **OR** `Replication Failed`

**Step 3-Bug-3.** If AI replication fails, **QA / Engineer** attempts manual replication on a **Manual Replication screen (TBD)**.
- Marks `Reproduced` or `Cannot Reproduce`
- Annotates RSD with findings (steps that worked, environment notes, video, etc.)

**Step 3-Bug-4.** Bug enters prioritization at `[D01]` Backlog with `Type=Bug`.
- Scored via Bug Severity model (not standard RICE — see §9.2 OL-B3)
- Then continues into standard Stage E (Delivery) like any other Backlog Item

### Stage C — Evaluation & AI Processing
**Step 6.** **PRODUCT LEAD** opens `[B04]` PRD Viewer to read the document.
- Tabs: Markdown · HTML Preview · Slide Preview · PDF · Images
- Uses TOC sidebar to navigate
- Optionally annotates inline, opens Version History drawer to diff against v2
- Forms a judgment

**Step 7.** **PRODUCT LEAD** opens `[B05]` PRD Evaluation queue.
- Finds the PRD in the Review Queue (filtered/sorted as needed)
- Opens evaluation panel (slide-out, 500px)
- Scores 4 criteria: **Completeness, Strategic Alignment, Technical Feasibility, Clarity & Quality** (1–5 stars each, optional comment)
- Writes Overall Assessment
- Clicks **Approve** / **Request Revisions** / **Reject** — provides mandatory rationale
- Submits Evaluation
- Artifact state: `PRD ↦ Approved` (or back to PRD Builder for revisions)

**Step 8.** **PM** opens `[C01]` Research & Analysis to investigate viability before scoring.
- Selects PRD as research subject
- Picks Research Mode: Quick Scan / Standard / Deep Dive
- **PM-BOT · Research Agent** runs prompts: Market Analysis · Competitor Scan · User Sentiment · Tech Feasibility · Full Research
- Live Report builds on the right (Executive Summary → Market → Competitive → Sentiment → Feasibility → Risk → **Priority Recommendation**)
- Recommendation card shows `Pursue / Defer / Reject` with confidence %
- Clicks "Attach to PRD" — research becomes a supplementary doc
- Artifact state: `ResearchSession ↦ Completed`, attached to PRD

**Step 9.** **PRODUCT LEAD** opens `[C02]` RICE Scoring for the same PRD.
- Three council agents (under PM-BOT umbrella, distinctly named): **Market Analyst**, **Technical Feasibility**, **Business Strategy** — each emits R/I/C/E numbers + commentary
- Aggregate RICE score is computed (e.g., 31.5 / 100, with 78–85% confidence range)
- Radar chart visualises Reach/Impact/Confidence/Effort dimensions
- Score history panel shows AI vs. consensus deltas
- Optionally overrides each dimension manually with audit note
- Artifact state: `BacklogItem ↦ scored`, eligible for prioritization

**Step 10.** **PM** opens `[C03]` SpecKit to break the PRD into engineering specs.
- Source PRD shown on the left
- **PM-BOT · Spec Agent** on the right generates User Stories (US-101, US-102…)
- Each story has Acceptance Criteria (auto-generated) + AI Confidence badge (signals Definition of Ready)
- PM uses toolbar: "Add more detail" · "Ensure accessibility" · "Generate Acceptance Criteria"
- "Transformation Velocity" footer shows accuracy-to-PRD %
- PM can edit, copy, or delete individual stories
- "Submit for PM Review" finalises the spec set
- Artifact state: `SpecItems ↦ Drafted`

**Step 11.** **PM** opens `[C04]` Figma Design Generation.
- Configures: Style (Wireframe / Low-Fi / **High-Fi**) + Screen scope (checklist)
- Clicks "Generate Designs" — **PM-BOT · Design Agent** populates gallery (states: Approved · Generating · Pushed to Figma · Draft)
- Opens any card → lightbox with variants strip + Linked Specs + Feedback thread + Refine & Regenerate input
- Approves variants; pushes selected designs to Figma
- Artifact state: `DesignScreen ↦ Approved`, `figma_frame_url` populated

### Stage D — Prioritization & Planning
**Step 12.** **PRODUCT LEAD** opens `[D01]` Backlog (Kanban view).
- Sees the new item land in the **Approved** column with RICE score badge (or Bug Severity badge if `Type=Bug`)
- Drags / clicks into details panel for full breakdown, links to PRD/Specs/RSD, Activity Timeline
- Clicks "Start Development" when ready

**Step 13.** **DOMAIN OWNER** (a Product Lead specialising in one domain) opens `[D02]` Domain Backlogs.
- Cross-Domain Summary at top: 5 domain cards (Payments / Onboarding / Risk / Growth / Platform) with stacked status bars and avg RICE per domain
- Selects own domain tab (e.g., Payments) — view filters
- Toggles between Ranked List / Board / Table
- Selects 2–4 items, clicks "Compare Selected" → full-width comparison panel opens (ephemeral within-session view; auto-save preserves selection only until tab close)
- Comparison shows side-by-side: RICE Breakdown · Consensus Score · Research Rec. · Evaluation · Impact/Effort · Dependencies
- "Winner Highlight" row identifies strongest item per dimension
- Marks chosen items as `Domain Priority` (star flag visible in Global Backlog)
- Clicks "Commit To Next Sprint Cycle" — **this is the persisted decision** (the comparison itself is not retained)
- Artifact state: `BacklogItem ↦ DomainPriority=true`, `domain_rank` updated

**Step 14.** **PRODUCT LEAD** opens `[D03]` Quarterly Roadmap.
- Gantt chart with TODAY indicator
- 5 domain rows, each showing initiative bars (Completed solid / In Progress hatched / Planned faded) with RICE badges
- Monthly Resource Allocation chart shows Dev/QA/Product capacity
- Strategic Capacity panel shows headcount (24/28 FTE) and budget ($420k / $600k)
- Roadmap Notes capture Q-objectives and resource shifting decisions
- Adjusts placement and resource allocation

### Stage E — Handover & Delivery
**Step 15.** **PM** opens `[D04]` Tech Handover Package.
- Checklist of artifacts: PRD Document ✓ · Speckit Specs ✓ · Figma Designs ✓ · 3rd Party Integration Docs (with one missing item flagged) · API Contracts ✓ · Acceptance Criteria ✓
- Right sidebar: 83% Handover Readiness donut, Done/Outstanding counts, Team Assignment dropdown, assigned Tech Lead
- Resolves any missing items, then clicks **"Send Handover"**
- Artifact state: `HandoverPackage ↦ Sent`, ownership transitions PM → Engineering

**Step 16.** **ENGINEERING LEAD** opens `[E01]` Delivery.
- Sprint scope view (currently Sprint 14) with 4 status cards: In Progress (7) / On Track (5) / At Risk (1) / Blocked (1)
- Detail table per initiative with progress bar, lead, target date
- Expandable rows show Commit Log, Critical Blockers, "Ready for Demo & UAT" CTA
- When item is ready, toggles UAT promotion

**Step 17.** **QA / TESTER** opens `[E02]` UAT Testing ("Precision Curator").
- Left: Acceptance Criteria checklist with Pass / Fail / Blocked / Skipped per item, screenshot capture per criterion
- Bug Report form (collapsible) — submitting routes the bug into Stage B-Bug
- Right: **PM-BOT · Test Agent** (chat) — proposes uncovered edge cases ("Insufficient funds retry", "Gateway timeout"), detects spec conflicts, offers to update spec
- Once all criteria pass, item is ready to release
- Artifact state: `BacklogItem ↦ ReadyToRelease`

**Step 18.** **PM (Release Manager)** opens `[E03]` Release Notes Editor.
- Selects release version (e.g., v2.4.0 — April 2026)
- Clicks "Auto-Generate from PRDs" — **PM-BOT · Release Notes Agent** drafts sections (New Features / Improvements / Bug Fixes / Known Issues) referencing PRD IDs
- Edits in rich text
- Right sidebar: ticks Audience checkboxes, picks Distribution Channels (Email/Slack/In-App/Confluence), curates Included PRD Items, sets Schedule
- Clicks **Publish**
- Artifact state: `ReleaseNote ↦ Published`, notifications fire

### Stage F — Outcomes
**Step 19.** **STAKEHOLDER** receives a release notification (default channels: email + in-app for v1; explicit settings come in v2 — see §9.1 OL-3).
- `[B03]` lifecycle for the original Request now shows `Released ✓`

**Step 20.** **EXECUTIVE / ANALYST** opens `[E04]` Success Metrics.
- KPIs: Ideas Submitted (47, +12%) · PRDs Generated (31, +8%) · Avg Time to Ship (23 days, –15%) · Release Adoption (78%, +5%)
- Submissions to Release Pipeline funnel chart
- Domain Distribution stacked bars
- Top Performing Releases table (Adoption %, Satisfaction stars, Impact level)
- RICE Score Accuracy scatter (R² = 0.84) — measures predicted vs. actual

### Out-of-band: Admin
**Anytime.** **ADMIN** opens `[Z01]` LLM Usage & Costs.
- Monthly Spend / Total API Calls / Avg Cost per PRD
- Daily LLM Spend chart with budget threshold line
- Model Configuration: per-feature LLM choice (PRD Generator / Research Bot) + max-token slider
- Cost Alerts at 50/75/90% thresholds
- Cost & Usage Breakdown table per feature (PRD Generator $1,142.50 · RICE Scoring $285.40 · UAT Assistant $945.20 · Research Bot $473.90)
- Tabs (greyed): Manage Users, Platform Settings (v2 scope — see §9.1 OL-4)

## 6. State-Transition Reference

Tables of the exact states each artifact moves through. Sourced from badges and labels visible in the screens (or, for new artifacts, from decisions captured in §9.1).

### 6.1 Request lifecycle (visible on `[B03]`)
```
Request Submitted → PRD Built → PRD Review → RICE Scoring → Backlog Approved → In Development → Released
```
For Type=Bug: substitute `RSD Drafted → AI Replication → (AI Replicated | Manual Replication) → Triaged` in place of `PRD Built → PRD Review`.

### 6.2 Brief status (`[B02]` `[B03]`)
```
v1 Draft → v1 Submitted → v1 Locked for Review → (eventually superseded by v2 if Stakeholder confirms)
```
Stakeholder can fork v(N+1) at any point after submit.

### 6.3 PRD status (visible across `[B02]` `[B04]` `[B05]`)
```
Draft (vN) → In Review → Approved → Final (vN) → Archived
```
Sub-state: each version is immutable; new versions are created on edit.

### 6.4 Spec Item status (`[C03]`)
```
Draft → In Review → Approved → Needs Revision (loops to Draft)
```
Plus AI Confidence: `High | Medium | Low` (Definition-of-Ready signal)

### 6.5 Design Screen status (`[C04]`)
```
Generating → Draft → Reviewed → Approved → Pushed to Figma
```

### 6.6 Backlog Item / Task status (`[D01]` Kanban columns)
```
New → Under Review → Approved → In Development → Released
```
Cross-cutting: `Type ∈ {Feature, Bug}`, `Domain Priority` flag (toggle), `Research Recommendation` (Pursue / Defer / Reject — Features only)

### 6.7 PRD Evaluation decision (`[B05]`)
```
Pending → In Review → { Approved | Revisions Requested | Rejected }
```
Decision requires rationale (min length enforced).

### 6.8 Delivery state (`[E01]`)
```
On Track | At Risk | Blocked  (orthogonal to In Progress / Released)
```

### 6.9 UAT criterion (`[E02]`)
```
Unset → { Pass | Fail | Blocked | Skipped }
```

### 6.10 Release Note (`[E03]`)
```
Draft → Scheduled → Published
```

### 6.11 Reproduction Steps Document (RSD) — bug path (NEW; no screens yet)
```
Draft → In AI Replication → { Replicated by AI | Replication Failed }
                                                       ↓
                                    In Manual Replication → { Reproduced | Cannot Reproduce }
                                                                      ↓
                                                                  Triaged → enters [D01] with Type=Bug
```

## 7. Key Decision Points

The places where the journey can branch — useful for designing demo scripts, regression tests, and stakeholder walkthroughs.

| Decision | Where | Branches | Downstream effect |
|---|---|---|---|
| Request type at intake | `[B01]` | New Idea / Change Request → PRD path; **Bug → RSD path (Stage B-Bug)** | Different artifacts and downstream pipelines per type |
| Brief supersession | `[B03]` (TBD prompt) | Supersede v(N) review with v(N+1) / Keep v(N) review running | If superseded, in-flight PRD Review on v(N) is closed |
| Approve PRD | `[B05]` | Approve / Request Revisions / Reject | Approve → `[C02]`; Revise → back to `[B02]`; Reject → terminates |
| Research recommendation | `[C01]` | Pursue / Defer / Reject (AI-generated, with confidence %) | Influences but does not gate `[C02]` RICE scoring |
| Manual RICE override | `[C02]` | Use AI consensus / Override with audit note | Override creates audit-logged divergence from agent assessments |
| AI Bug replication outcome | Bug Workspace (TBD) | Replicated by AI / Failed (handed to human) | Failed → routes to QA Manual Replication screen (TBD) |
| Manual Bug replication outcome | Manual Replication (TBD) | Reproduced / Cannot Reproduce | Both ↦ Triaged; Cannot Reproduce flagged for follow-up with Stakeholder |
| Domain Priority flag | `[D02]` | Flagged / Unflagged | Flagged items surface as starred in `[D01]` Global Backlog |
| Sprint commitment | `[D02]` | Commit to Next Sprint Cycle / Defer | Commits move into `[E01]` Sprint scope (decision persisted; comparison not) |
| UAT outcome | `[E02]` | All Pass / Any Fail | Pass → ready for release; Fail → bug created (routes via Stage B-Bug) |
| Release publish | `[E03]` | Publish / Save Draft / Schedule | Publish triggers notifications to all subscribed Stakeholders |

## 8. System Behaviours (PM-BOT as actor)

PM-BOT is the umbrella AI brand. It acts via specialist sub-roles per surface — except RICE Scoring, where three independently-named council agents operate under the umbrella.

| Where | Sub-role | What it does | Output | Human override |
|---|---|---|---|---|

## 9. Open Loops & Notes for Future Iteration

### 9.1 Resolved (decisions captured 2026-04-19)

| ID | Question | Resolution |
|---|---|---|
| OL-1 | Brief locking semantics | Once PM review starts, Brief vN ↦ **"Locked for Review"**. Stakeholder cannot edit vN; can create v(N+1) in parallel and submit. v(N+1) does NOT auto-supersede; explicit Stakeholder confirmation required (see OL-B1). |
| OL-2 (Q4) | Bug-vs-Idea flow divergence | New pipeline: `Bug → RSD → AI Replication → human fallback → prioritization`. Requires new artifact (RSD §2.7), new agent (PM-BOT · Bug Replication Agent), and new screens (Bug Workspace, Manual Replication, possibly Triage). See OL-B2/B3/B4/B7. |
| OL-3 | Notification settings screen | **v2 scope.** v1 ships with default channels (email + in-app) on for everyone. Document as placeholder. |
| OL-4 | Manage Users / Platform Settings | **v2 scope.** v1 manages via direct DB / config. Greyed previews on `[Z01]` stay; document as placeholder. |
| OL-5 (Q5) | Submission Score formula | Becomes a **build task**: design a small algorithm. Suggested input dimensions: (a) section completeness, (b) section depth, (c) specificity signals (numbers, dates, named systems, attachments), (d) average AI confidence per generated section. Algorithm spec to be drafted separately. |
| OL-6 | Comparison panel save state | **Comparisons are ephemeral** within-session views. Auto-save preserves selection only until tab close. Persistent outcomes are the prioritization decisions ("Commit To Next Sprint Cycle"), not the comparisons themselves. |
| OL-7 | AI Confidence vs Submission Score | **Two distinct readiness signals at distinct stages.** Submission Score = "PRD is ready for product team to review" (`[B02]` `[B03]`). AI Confidence = "Spec meets Definition of Ready for engineering planning/development" (`[C03]`). No reconciliation — keep both names; document the distinct purposes (done in §2.2 and §2.3). |

### 9.2 New open loops surfaced by the resolutions

| ID | Open question | Why it matters |
|---|---|---|
| **OL-B1** | Brief v(N+1) supersession UX. When Stakeholder submits v(N+1) while v(N) is locked under review, what's the prompt? "Supersede current review?" Concurrent reviews? Auto-merge? | Without a defined UX, parallel Brief versions create review-state ambiguity. |
